Assignment 3 Reflection Report

The implementations in Assignment 2 and Assignment 3 perform the same ETL workflow, but the designs differ significantly in structure, clarity, and organization. Assignment 2 uses a primarily procedural approach: most of the logic—file reading, parsing, validation, transformations, formatting, and summary reporting—resides in one large `main` method inside a single class. While this approach works for small programs, it blends responsibilities and creates a tightly coupled structure that becomes difficult to extend or modify. Adding or adjusting transformation rules requires manually editing the same long method, which increases the likelihood of introducing errors. All helper functionality, such as CSV splitting and money formatting, is implemented as static methods rather than belonging to meaningful abstractions. As a result, Assignment 2 behaves correctly but lacks clear separation of concerns.

Assignment 3, by contrast, reorganizes the solution using object-oriented principles. Instead of concentrating everything in `main`, the task is decomposed into multiple classes, each with a single, well-defined purpose. The `Product` class encapsulates the state of each record, storing fields like name, price, category, and price range with private attributes and controlled access through getters and setters. File input and output are delegated to `CsvProductIO.Reader` and `CsvProductIO.Writer`, which handle reading a CSV file and writing transformed records to an output file. The transformation logic is broken into several classes that implement a common `Transformation<Product>` interface, including `UppercaseName`, `ElectronicsDiscountRule`, `CategoryUpgradeRule`, and `PriceRangeDeriver`. These rules are applied polymorphically by the `Pipeline` class, which orchestrates the ETL sequence—reading each record, applying each rule in order, writing to the output file, and tracking metrics such as rows read, skipped, and transformed. This redesign makes the system modular, easier to read, and significantly more scalable.

Several core object-oriented concepts are used in the Assignment 3 implementation. The notions of **objects** and **classes** appear in the clear mapping of real-world concepts—products, readers, writers, and transformation rules—to dedicated classes. **Encapsulation** is demonstrated through the `Product` class, which hides internal fields and exposes only necessary operations, as well as in `Pipeline` and the I/O classes that manage their own internal processing. **Inheritance** is used in the design of the `PriceRule` abstract class, which defines a template for modifying prices and enforces consistent rounding. The subclass `ElectronicsDiscountRule` inherits this structure and supplies its own discount logic. **Polymorphism** is central to the design, where the pipeline interacts with each transformation through the shared `Transformation<Product>` interface. This makes the pipeline open to extension but closed to modification—new transformations can be added without changing the pipeline’s code.

To confirm that Assignment 3 produces the same results as Assignment 2, I performed several tests. First, I used the same `products.csv` input file that I used in Assignment 2. After adjusting the pipeline’s row‑counting behavior so that “rows read” reflects all non-header lines (including rows that will be skipped), the summary produced by Assignment 3 matched Assignment 2 exactly: the same number of rows read, transformed, and skipped. Next, I compared the output `transformed_products.csv` files line-by-line. The transformed names, prices, categories, and price range values were identical in both outputs, and the money formatting matched Assignment 2’s exact two-decimal behavior. I also verified that invalid rows—such as those with missing fields, blank lines, or invalid numeric values—were skipped in both versions. Together, these tests confirmed that the object-oriented redesign preserved functional correctness while greatly improving the structure and maintainability of the program.
